第六十批交付报告 · iOS 导出丢图的真因

2026-10-21　｜　人格卡「有文字背景全白」· 方形图「专辑旁特效错位」· 竖形图「冠军没图」

一句话结论：不是 CSS 写错，也不是跨域 —— 是 WebKit 把图画空了，而且一句错都不报。 同一张图，Chromium 里 24×24 里 576/576 个不透明像素一次就对；WebKit 里 naturalWidth=1080、decode() 也返回成功，但 drawImage() 之后画布是空的 —— toDataURL() 只给出 "data:,"（6 字节），或者直接抛 InvalidStateError。

一、为什么桌面端一直正常

因为桌面用 Chromium/Blink：图片落到画布是同步就绪的。Safari / iOS 的 WebKit 不是 —— SVG 里的 foreignObject 与内嵌图片的位图不是同步就绪，首次截图时图片往往还没画上。 这是社区记录多年的固有行为（html-to-image #461「Blank Image in Safari」、dom-to-image 的 「Safari 下图片偏移/部分缺失/整块空白」避坑条目；三方对比里 html-to-image 首次调用在 WebKit 丢照片、 modern-screenshot 靠 delay 参数绕开）。

所以「别人的 App 能实现」是因为它们做了三件事之一：等一帧再画、连续生成两次、 或干脆不用 foreignObject（html2canvas 那种自己画像素的路）。

二、我们为什么会"图丢了还说成功"

1
取图那一步把"空白"当成了"成功"
redrawToB64() 只要 toDataURL() 不抛就当有效图 —— 而空白画布返回的是 6 字节 "data:,"，或者干脆抛错被 try 吞掉。
2
内联失败时静默留外链
拿不到 dataURL 就 continue，<img src="http://…"> 原样留在 SVG 里。 而 SVG 当图片用时一条外链都加载不了 ⇒ 那张图必然空白（人格卡整卡纯白的直接原因： .pcard 本身没有底色，全靠 .bg 这张图）。
3
校验把"读不了"判成了"通过"
imagesSeemPresent() 在 getImageData 抛错时 return true（本意是"测不了就别误伤"）。但画布被污染的唯一成因就是导出内容引用了外部资源 = 一定有图没进去。于是坏图一路"过检"，永远轮不到兜底引擎。

三、这次改了什么

位置改前 → 改后
saveImage.js 新增 canvasHasInk()：画完读回像素，全透明就是没画上。
redrawToB64 改 async：先 24×24 试画 → 空就等一帧重画（40/120/260ms，最多 3 次） → 仍空则返回 null，不再用空白 dataURL 冒充成功。
新增 bytesToB64()：fetch → blob → FileReader 取原始字节， 完全不经过画布，并提到画布之后第一步 —— 这是 iOS 上的确定性兜底。
没内联上的图必须 console.warn 报数。
cardExport.js inlineImages 的画布路同样加像素校验；
imagesSeemPresent 在 getImageData 抛错时 true → false；
exportNodeToPng 拆出 renderViaSvg()，改成 SVG 试 2 次（中间双 rAF + 260ms）→ 才退 html2canvas（html2canvas 会丢 calc(var()) 间距，只能是最后一道）；
materializePseudo：凡 inset:0 的"铺满宿主"伪元素， 盒子按宿主像素矩形钉死 + 显式 box-sizing: border-box。
「特效错位」为什么这样修：把你给的那张方形图放大看，那块东西是 横平竖直的硬边柔和的径向渐变 —— 正是 .scard.glassy::before（顶部压暗 + 冠军色柔光 + 纱幕）被画到了错误位置和尺寸。 伪元素不是真元素，getComputedStyle(el,'::before') 的位置/尺寸在不同引擎里可能是 auto，那层渐变就被丢到静态位置、按内容大小渲染。现在直接按宿主矩形钉死，视觉上完全等价， 但不再依赖引擎对伪元素的计算结果。
