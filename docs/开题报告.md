论文题目：音乐专辑评选与人格测评互动平台设计与实现

## 摘要

针对现有音乐应用以单向推荐与数据回顾为主、用户参与深度有限的问题，本文设计并实现一个以"专辑评选（对决）"与"音乐人格测评"为核心玩法的音乐互动平台。平台采用前后端分离架构：前端基于 Vue 3 与 Element Plus 实现交互界面，后端基于 Node.js 与 Express 提供业务接口，数据存储采用 MongoDB；音乐数据通过开放接口获取并缓存至本地数据库，测评结果的个性化解读由大语言模型生成。平台实现了对决赛制自动生成、逐轮投票、晋级与复活、试听播放、结果可视化与分享图导出等功能，并完成云端部署与上线。测试结果表明，系统功能完整、数据流转真实，能够支持用户以游戏化方式完成音乐偏好的表达与分享。

关键词：音乐互动应用；专辑对决；音乐人格测评；Vue3；全栈开发

## 一、选题背景及意义

本部分说明课题的提出依据。先从数字音乐消费行为的转变出发，阐述"比较需求"与"人格化表达需求"的形成；再从实用、技术、专业与数据四个层面说明本课题的价值。

### 1.1 选题背景

近年来，数字音乐已成为大众文化消费的主要形式之一。随着流媒体平台的普及，用户获取音乐的边际成本趋近于零，音乐消费的行为重心也从"寻找并收听歌曲"逐步转向"表达偏好、相互比较与社交分享"。在这一转变过程中，两个现象值得关注。

一是用户的比较需求长期缺乏工具支撑。音乐爱好者普遍存在"同一歌手的哪张专辑更好"这类讨论，但现有音乐应用的产品形态以"推荐—播放"为主线，用户始终处于被动接受推荐的位置；当用户试图系统性地比较、评选自己喜爱的作品时，缺少顺手的工具，只能依赖聊天群内的口头讨论，过程零散且难以留存。

二是"人格化标签"具备较强的传播能力。以 MBTI 为代表的人格测试类内容在社交网络中持续保持高传播度，其原因在于测试结果兼具自我认知与社交表达的双重功能。音乐偏好本身就是个体自我认知的重要组成部分，将音乐偏好转化为可解读、可分享的人格标签，具备明确的产品价值。

从技术条件看，本设计的实现基础已经成熟。其一，Vue 3 与 Node.js 构成的前后端分离技术栈发展成熟，社区生态完善，适合中小型互动应用的快速实现；其二，以 iTunes Search API 为代表的开放音乐数据接口可在无需密钥、无需账号授权的条件下提供音乐元数据与官方试听片段，使音乐类应用能够在不涉及版权风险的前提下合法获取展示素材；其三，大语言模型接口的调用成本显著下降，使"为每个用户生成个性化文本"这类过去难以承担的功能具备了工程可行性。

### 1.2 研究意义

实用意义。本平台把用户面对"选择困难"时的模糊倾向，转化为一场规则明确、过程可见的对决；同时把难以言说的音乐偏好，转化为一张可解读、可分享的人格画像。两种玩法均以"用户主动参与并产生数据"为前提，与现有产品的单向展示形态形成区别。

技术意义。本平台是一个完整的前后端分离全栈应用，覆盖数据库设计、接口服务、用户认证、数据可视化与云端部署等环节，能够完整呈现一个 Web 应用从需求分析到上线运行的全过程，具备较好的工程实践价值。

专业意义。本设计聚焦交互机制设计与视觉呈现设计，其结果可视化与分享图生成环节直接体现数字媒体技术在视觉表达与内容生成方面的专业能力，符合数字媒体技术专业的培养方向。

数据意义。平台在运行过程中会沉淀用户的偏好数据与测评结果数据，形成可统计分析的数据集，为音乐推荐策略与社群运营研究提供参考。

## 二、国内外研究现状综述

本部分从学术研究与应用产品两个层面，分别梳理国外与国内的相关工作，并在此基础上归纳出现有研究与实践尚未充分满足的空白，作为本课题的切入点。

### 2.1 国外研究与应用现状

在学术研究层面，音乐推荐长期是信息检索与用户建模领域的重要方向。Schedl 等在其综述中指出，音乐推荐系统面临冷启动、序列依赖、多模态特征融合等核心挑战，并强调用户显式反馈数据（如收藏、评分、对比选择）在提升推荐质量中的价值。在人格与音乐偏好的关系研究方面，Rentfrow 与 Gosling 通过大规模调查提出音乐偏好与人格特质之间存在稳定关联，为"由音乐偏好推断个体特征"提供了实证依据。在互动机制层面，Hamari 等对游戏化研究的系统综述表明，游戏化设计对用户参与度与持续使用意愿具有正向影响，但其效果高度依赖具体机制设计与使用情境，不能简单套用。

在应用产品层面，可归纳为两类。第一类是年度回顾型，如 Spotify Wrapped 与 Apple Music Replay，产品以平台侧积累的用户行为数据为基础，生成个性化的年度总结并与用户分享，其特点是传播效果好，但用户全程处于"接受结果"的位置。第二类是互动评选型，如以音乐对决、歌单投票为玩法的社交应用，把用户之间的比较行为本身做成了玩法，用户在其中的每一次选择都会留下数据。值得注意的是，这两类产品的数据基础均为平台自有曲库与自有用户行为记录，对外部开发者并不开放。

### 2.2 国内研究与应用现状

国内主流音乐平台同样以年度听歌报告作为主要的用户互动节点，形式上以统计数据与可视化的单向呈现为主；在社交玩法上主要集中于"一起听"与"歌单共创"，缺少围绕"评选与对决"的强互动形态。

在高校毕业设计与课程作品层面，与本课题相关的工作大量集中在"文化数字化展示平台"与"信息展示类小程序"两类。前者以图文陈列、三维模型展示、沉浸式浏览为主，后者以信息检索、预约管理、增删改查为主。这两类作品普遍存在两个共同的局限：一是交互深度有限，用户以浏览为主，系统不产生由用户决策驱动的数据；二是数据来源多为静态录入，系统与外部真实数据的流通较少。

在人格测评类应用方面，MBTI 类测试的传播度很高，但其实现方式多为"问卷作答 + 固定文案模板"，即同一类型的用户会得到完全相同的解读文本，个性化空间有限，也较少与音乐这类强感官刺激的媒介相结合。

### 2.3 研究现状小结

综合国内外研究与应用现状，可归纳出三个尚未被充分满足的空白。

第一，参与深度不足。现有产品的交互范式基本为"浏览—接受"或"作答—查看结果"，用户的决策行为要么不被记录，要么仅作为一次性输入，无法形成可累积、可对比、可再消费的数据资产。

第二，音乐数据获取的合法性约束常被忽视。音乐类应用对曲库依赖性极强，部分作品依赖非公开接口或未授权音频资源，存在版权风险与稳定性风险，导致作品难以公开部署与长期运行。

第三，测评结果的个性化程度低。现有音乐标签与人格测试多采用固定文案模板，缺乏针对个体作答组合的差异化解读，且很少把"听感"这一音乐特有的感知维度纳入测评过程。

基于以上三点，本课题提出以"专辑对决"与"音乐人格测评"两种互补玩法为核心，构建一个数据自体闭环、可公开部署、结果个性化生成的音乐互动平台，并在此基础上完成毕业作品与论文。

## 三、研究内容与拟解决的关键问题

本部分先明确课题要达到的总体目标，再将其拆解为十项可实施、可验证的具体研究内容，最后列出实现过程中必须解决的关键技术问题。

### 3.1 研究目标

设计并实现一个以"专辑对决"与"音乐人格测评"为核心玩法的音乐互动平台，完成前后端开发、数据库设计、云部署与上线发布，形成一套可公开访问、功能完整、数据真实流转的应用系统，并在此基础上完成毕业论文的撰写。

### 3.2 研究内容

（1）需求分析与交互设计。通过功能拆解与用户故事梳理明确系统边界，完成用户故事清单、功能需求与非功能需求（性能、安全、可用性）的整理；输出完整的界面设计稿，覆盖前台用户端与后台管理端。

（2）系统架构设计。采用前后端分离的三层架构，明确展示层、业务服务层与数据层的职责划分，完成系统架构图与数据流转说明。

（3）数据库设计。围绕用户、音乐数据、对决过程、测评数据四类对象完成数据库建模，设计用户、歌手、专辑、曲目、对决、对战场次、投票、测评题目、人格类型、测评结果、收藏、分享记录等数据表，明确实体间关系并输出实体关系图。

（4）音乐数据获取与缓存模块。通过开放接口获取歌手、专辑、曲目及试听资源，完成字段规范化映射与数据持久化，并设计缓存更新策略。

（5）专辑对决模块。实现对阵自动生成、逐轮投票、晋级与复活机制、结果汇总与冠军生成；提供对决过程中的试听能力，使用户在未听过专辑的情况下也能做出选择。

（6）音乐人格测评模块。完成题目体系设计、计分模型与类型映射规则；实现包含试听感知题的作答流程，并输出人格结果卡片与推荐专辑。

（7）大语言模型文本生成模块。将用户作答组合与测评结果作为输入，生成个性化解读文案；设计提示词模板、异常降级与结果缓存机制。

（8）数据可视化与分享图生成模块。实现对决对阵图、冠军路径图、人格卡片的绘制与图片导出；完成平台榜单与人格类型分布的统计可视化。

（9）后台管理模块。实现数据看板、测评题目管理、人格类型管理、音乐数据管理与用户管理功能。

（10）系统测试与部署上线。完成功能测试、接口测试、兼容性测试与用户试用反馈收集；将前端、后端与数据库分别部署至云平台，获得可公开访问的线上地址。

### 3.3 拟解决的关键问题

（1）音乐数据的合法获取、规范化与缓存。需选用无版权风险的开放接口作为数据源，对多语种、多地区返回的异构数据做统一规范化处理；并设计缓存策略，将外部接口数据持久化至本地数据库，以降低外部依赖、提升响应速度并规避接口频率限制。

（2）对决赛制算法的设计与体验平衡。需设计可供程序自动生成的对阵结构，处理参赛数量非 2 的整数次幂时的轮空问题，并在淘汰赛之外补充复活机制。同时必须控制单场赛事的整体时长，避免赛程过长导致用户中途流失。

（3）音乐人格测评模型的构建。题目的设计、维度划分、计分规则与类型映射共同决定结果的有效性与区分度，需要在题目数量（兼顾体验时长）与结果准确性之间取得平衡，并保证同一用户重复作答时结果具备稳定性。

（4）个性化文本生成的质量与成本控制。大语言模型输出的稳定性与时延直接影响体验，且存在调用失败的可能，需设计合理的提示词结构以保证风格统一，并建立降级机制。

（5）结果可视化与分享图的跨设备一致性。对阵图与人格卡是核心视觉产出，需在不同屏幕尺寸与浏览器下保持版式一致，尤其要解决中文字体渲染与内容截断问题。

（6）系统的安全性、性能与可部署性。需完成用户认证与数据安全设计，实现接口鉴权与输入校验；通过合理的缓存与索引策略保证响应性能；最终完成云端部署，提供可公开访问的线上地址。

## 四、研究方法与技术路线

本部分说明课题的实施方式。先列出所采用的研究方法及其用途，再给出从开发方法、前后端技术、数据存储、外部服务到部署方案的完整技术路线，最后汇总关键技术选型。

### 4.1 研究方法

文献研究法。查阅音乐推荐、用户行为分析、人格与偏好关系及游戏化设计相关文献，明确研究现状与技术选型依据。

需求分析法。结合同类产品的功能对比与目标用户的功能诉求，梳理功能清单与非功能需求，形成需求分析文档。

原型迭代法。先完成界面原型与核心交互流程设计，再进入编码实现；在实现过程中结合试用反馈持续迭代。

对比实验法。针对对决机制的关键参数（参赛作品数量、是否启用复活赛）进行对照试用，依据完成率与主观反馈确定最优方案。

软件工程方法。遵循需求分析、概要设计、详细设计、编码、测试、部署的工程流程组织开发工作，并使用版本控制工具管理代码演进。

### 4.2 技术路线

开发方法。以迭代开发组织进度，每个迭代产出可运行版本；在实现环节引入人工智能辅助编程工具提升开发效率，同时保证核心设计与关键逻辑由本人完成与验证。

前端技术。采用 Vue 3 作为核心框架，配合 Vite 构建、Vue Router 路由、Pinia 状态管理与 Axios 数据请求；界面组件采用 Element Plus；音乐试听使用浏览器原生音频能力实现；结果分享图借助前端绘图转换库生成。

后端技术。采用 Node.js 运行环境与 Express 框架搭建业务服务，实现音乐数据代理与缓存、对决与测评业务接口、排行榜统计接口及后台管理接口；用户认证采用 JSON Web Token 方案，密码采用单向加密存储。

数据库技术。采用 MongoDB 文档数据库存储数据，通过 Mongoose 完成数据建模与校验。

外部服务。音乐数据来自 iTunes Search API，用于获取歌手、专辑、曲目及官方试听片段；个性化文本生成调用大语言模型接口。

部署方案。前端部署至静态托管平台，后端部署至云应用托管平台，数据库使用云端数据库服务，形成前后端与数据库三端独立部署的结构，保障线上环境的可访问性与稳定性。

## 五、进度安排

本课题计划用六周完成作品开发与论文撰写，各阶段均设置可交付成果，以便按周检查进度。时间安排兼顾日常课程与求职安排，将工作量均匀分布而非集中在期末。

第一阶段（第 1 周）——需求分析与系统设计。完成需求分析文档、系统架构图、数据库实体关系图与全部界面设计稿，搭建代码仓库并完成首次提交。

第二阶段（第 2 周）——后端与数据库实现。完成数据表建模、用户认证模块、音乐数据获取与缓存模块，以及对决、测评、榜单与后台管理等业务接口的开发与联调。

第三阶段（第 3 周）——前端页面与核心玩法实现。完成前台与后台全部页面的开发，实现专辑对决与音乐人格测评两条完整业务流程，完成试听播放与分享图生成功能。

第四阶段（第 4 周）——模型接入、后台完善与部署上线。完成大语言模型文本生成模块及其降级机制，完善后台管理功能，完成三端云部署并获取线上访问地址。

第五阶段（第 5 周）——系统测试与用户反馈。开展功能测试、接口测试与兼容性测试，组织不少于 5 名用户进行试用并收集反馈，针对问题完成优化与迭代。

第六阶段（第 6 周）——论文撰写与答辩准备。整理开发过程材料与图表，完成毕业论文初稿；根据指导意见修改完善，制作答辩演示文稿，准备系统演示与答辩。
