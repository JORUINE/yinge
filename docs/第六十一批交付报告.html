一句话结论：暗带不是 CSS 写错，也不是渐变，是 .art 的 box-shadow 被 WebKit 的 SVG(foreignObject) 栅格化成了硬边深色矩形； 而图片"有时在有时不在"的根子是 首帧竞态 —— 同一个 SVG，decode() 之后 立刻取像连续 6 次全空，中间等 120ms 连续 3 次全对。

一、暗带到底长在哪

把 WebKit 导出的方形图逐像素扫一遍，可以把它钉到具体坐标（CSS px，相对卡片）： 封面右缘 x≈350、暗带一直到 x≈412、上下与封面同高（y 112~347）—— 62px 宽、与封面等高的一块硬边矩形。同一张卡左侧对称区的亮度是 137.2，这块只有 34.9。

归因实验（每一步只改一个变量，可复跑）：
操作暗带区亮度判定
① 基线32.7暗带在
② 去掉 .art 的 box-shadow125.6暗带消失
③ 换成 filter: drop-shadow()125.6不画阴影、也不出现暗带
④ 去掉 ::after / ::before / backdrop-filter30~42都不影响
⑤ 阴影参数改成 0 偏移 / 0 模糊34.1与参数无关

结论：只要这层 box-shadow 进了 SVG，WebKit 就把它画成硬边块； 换 drop-shadow 虽然不出现暗带，但阴影整个丢了（亮度＝完全没阴影）。

二、修法：阴影不进 SVG，由 canvas 自己画

1
克隆里把"图片容器"的阴影关掉
用临时属性标记（data-yinge-shadow-off）而不是"下标配对"—— 因为 materializePseudo 会往克隆树里插入伪元素 div，下标会错位（我第一次就栽在这，静默失效）。
2
按同一组参数用 canvas 画回来
parseShadows() 解析 rgba(...) 0px 18px 44px 0px； paintShadow() 在设备像素里画（canvas 的 shadowBlur/Offset 不吃 CTM， 混用会画到别处），再 destination-out 把形状本体挖掉，只留"形状之外"的柔和投影。
3
引擎策略（定稿）
桌面 Chromium/Edge/OPR/Firefox → SVG（产物逐字节不变）； WebKit（iOS Safari / 微信 / macOS Safari）→ 直走合成，不等竞态； 未知引擎 → 先用「封面量级 600×600」的图做一次首帧能力自测；html2canvas 仍是最后一道。

四、一个被纠正的旧结论

上一轮写的是「SVG(foreignObject) 在 WebKit 里根本不渲染内嵌图片」。这次用对照实验改成更准确的说法： 不是不渲染，是首帧没就绪 —— 立刻取像 alpha=0（6/6），等 120ms 就正常（3/3）。 这意味着："试两次 SVG"不是完全没用，但等待时间无法保证（卡里的图比测试图大得多）， 所以 iOS 仍然直接走合成，不赌竞态。
