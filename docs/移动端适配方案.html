7实施过程中抓到的三个大坑（都已修，写进守则）

坑现象 → 根因 → 修法
backdrop-filter 造包含块手机底栏"贴底"贴到了 1149px（视口只有 780px）。 根因：.stage 有 backdrop-filter: blur(22px)，它给后代的 position:fixed 造了一个包含块，底栏不再是相对视口定位。 修法：遮罩 / 弹层 / 底条三者全部 Teleport 到 body。
z-index 造层叠上下文点「开始对决」被弹层拦截（elementFromPoint 返回弹层）。 根因：.shell 有 z-index:1，自己造了层叠上下文， 底条的 z-index:80 被困在里面，整体（z=1）输给弹层（z=70）。 修法：Teleport 到 body 后层级才真正生效（65 < 70 < 80）。
CSS 特异性平局手机端封面被算成 312×312，而两张卡各只有 119.5px 宽 ⇒ 严重溢出、左右叠在一起。 根因：.pk-only .duelgrid .alb .art 与 .play .duelgrid .alb .art 特异性同为 3 类，源码靠后者赢。 修法：选择器抬到 4 个类（.play.pk-only …），封面改 width:100% + aspect-ratio:1/1 撑满自己那一列。
模板标签丢失串行编辑时丢掉了一个 </div>，浏览器报 Element is missing end tag。修法：写了个标签栈配对脚本定位（该脚本自己先被 \r\n 绊了一次，加 .replace(/\r\n/g,'\n') 才好）。

8顺带修掉的一个真 bug：歌手搜索排序

手机端到端探针跑第 2 遍时突然报红（第 1 遍是全绿的）—— "点候选里的加入 → 摘要跟着变"失败了。我没改探针去迁就它，而是去查了根因，结果是产品真 bug：
  • 现象：搜简体「周杰伦」，候选列表第一位是卡拉OK/翻唱团「周杰伦战队」， 真正的「周杰倫」被挤到第 3 位。用户点第一个「加入」→ 池子里是一位 0 张专辑的野鸡歌手， 摘要永远停在「还没选完」，观感就是"加了人却开不了局"。
  • 根因：matchScore() 里「名字以搜索词开头 → 900 分」， 压过了「简繁/拼写近等 → 333 分」。而这个函数本来就是为"手滑漏字母"写的， 现在反过来了：名字更长被当成强证据，同名字的另一种写法只算 1 个字符。
  • 为什么第 1 遍没暴露：iTunes 的实时搜索结果会变 —— 那两位野鸡歌手是后来才出现在结果里的。 这条正好说明探针必须跑真的接口、不能 mock。
  • 修法（对每一位歌手都成立，不靠名单）：按"是不是同一个名字的不同写法"重新分档 —— ① 完全相等 1000；② 等长且只有 1~2 处替换 → 940 起（周杰倫/周杰伦、travisscoot/travisscott）； ③ 名字以搜索词开头 → 900 − 多出字符数×30；④ 互相包含；⑤ 公共前缀比例兜底。 等长近等 > 前缀命中是本次修复的核心。另加一条曲库在场证据的微弱加分 （cached / albumCount 是接口真实字段），只在名字分接近时打破平局。
  • 顺带补的一个人话提示：加了 0 张专辑的歌手时，以前界面毫无反应。 现在会弹「没有可参赛的正式专辑（可能是卡拉OK / 翻唱 / 合辑），换一位歌手试试」， 且常驻提示里点名这位歌手、并保证参赛张数不会被虚报撑大。
  • 已知取舍（如实记录）：等长近等优先之后，搜 2 字前缀（如「王力」）时， 同为 2 字且差 1 字的「王菲」会排在「王力宏」前面。换来的收益是：搜「周杰伦」「陶喆」这类 全名查询时真正的歌手永远第一 —— 全名查询才是这个页面的主场景。
验收（probe-r42-search-rank.mjs，12 条断言，判据刻意独立于被修的那条规则）： 用① 接口真实字段 cached/albumCount、② iTunes 自己返回的第一条、③ 与查询词的普通（不加权）Levenshtein 距离 三条外部事实来判断，不重新实现 matchScore 自己判自己。 实测：候选顺序变成「周杰倫(曲库) → 周杰伦战队(未入库) → 周杰伦子(微唱)(未入库) → 周深 → 王力宏 → 林俊傑」， 点第一个「加入」摘要真的变成"已选 8 张 · 来自 1 位歌手 · 共 5 场"。
