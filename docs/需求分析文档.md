## 一、文档说明

### 1.1 编写目的

本文档用于明确"音格"平台的功能边界与质量要求，是后续系统设计、界面设计、编码实现与测试验收的共同依据。本文档回答三个问题：系统要做给谁用、系统要实现哪些功能、系统必须达到怎样的质量水平。

### 1.2 项目概述

音格是一个以"音乐专辑对决"与"音乐人格测评"为核心玩法的音乐互动平台。平台通过开放音乐数据接口获取真实音乐数据，让用户以游戏化的方式完成两件事：一是对自己喜爱的作品进行评选与对比，二是获得基于自身音乐偏好的个性化人格画像。

与现有音乐应用不同，本平台不提供完整曲库播放，而是聚焦于"比较"与"表达"这两类被长期忽视的用户行为，把用户的选择行为沉淀为可累积、可统计、可分享的数据资产。

### 1.3 术语与缩写

| 术语 | 说明 |
| --- | --- |
| 对决 | 由用户发起的一次专辑评选活动，包含若干轮比赛 |
| 场次 | 对决中的一场两两比较，由两张专辑对战 |
| 轮空 | 参赛专辑数为奇数时，某张专辑本轮无需比赛直接晋级 |
| 复活赛 | 在小组赛之后额外安排的轮次，给落败专辑再次晋级的机会 |
| 人格类型 | 音乐人格测评的最终结果分类，每类对应一段解读文本 |
| 试听片段 | 由音乐数据接口提供的 30 秒官方音频片段，用于辅助投票 |
| 分享图 | 由系统生成的可保存、可转发的图片，用于结果传播 |

### 1.4 读者对象

- 指导教师与答辩评审：了解系统的需求来源与设计依据；
- 开发者（本人）：作为编码与测试的依据；
- 后续维护者：理解各功能的用途与约束条件。

## 二、项目背景与建设目标

### 2.1 项目背景

数字音乐已成为大众文化消费的主要形式，但现有应用的产品形态高度同质：以"推荐—播放"为主线，用户长期处于被动接受内容的位置。当用户产生"同一歌手哪张专辑更好"这类比较需求时，缺少顺手的工具，只能依赖聊天群内的口头讨论，过程零散且无法留存。

与此同时，以性格测试为代表的"人格化标签"内容在社交网络中保持高传播度，其原因在于测试结果同时满足自我认知与社交表达两种需求。但现有音乐类测评普遍采用固定文案模板，同一类型的用户得到完全相同的解读，个性化程度低，也很少把"听感"这一音乐特有的感知维度纳入测评选型。

### 2.2 建设目标

设计并实现一个可公开访问的音乐互动平台，达成以下目标：

（1）实现对决与测评两条完整可用的业务流程，用户从进入到获得结果全程无阻断；

（2）实现真实的数据流转，系统的内容由用户行为与外部数据共同产生，而非静态展示；

（3）实现结果的可视化与可分享，使平台具备自传播能力；

（4）完成前端、后端与数据库三端的云端部署，提供可公开访问的线上地址；

（5）在实现过程中形成完整的需求、设计、测试文档，满足毕业设计的过程性要求。

### 2.3 目标用户

| 用户角色 | 特征描述 | 核心诉求 |
| --- | --- | --- |
| 游客 | 未注册的访问者 | 快速了解平台玩法，无需注册即可体验部分内容 |
| 注册用户 | 音乐爱好者，追求参与感与社交表达 | 发起对决、参与投票、获得人格卡并分享 |
| 活跃用户 | 频繁使用、关注榜单变化 | 查看历史记录、收藏专辑、观察榜单趋势 |
| 后台管理员 | 平台维护者 | 维护题目与人格类型、管理音乐数据与用户 |

### 3.2 关键用户故事详述

**US-03 按范围发起对决**

作为注册用户，我想按歌手挑选范围，以便只比较我关心的作品。

验收标准：

（1）支持按歌手名称搜索，输入关键词后返回候选歌手列表；

（2）选定歌手后自动获取其全部专辑，含封面、发行日期与曲目数；

（3）当获取到的专辑少于 4 张时，提示用户更换范围，不进入对决流程；

（4）专辑数据同时写入本地数据库，重复发起时直接读取缓存，不再请求外部接口。

**US-05 投票前试听**

作为注册用户，我想在投票前试听专辑片段，以便在没听过的情况下也能作出选择。

验收标准：

（1）每一场对战的两张专辑均可播放 30 秒试听片段；

（2）同一时刻只允许一个音频在播放，切换专辑时自动停止上一个；

（3）若某张专辑没有可用的试听片段，界面明确提示而不显示失效的播放按钮；

（4）试听不阻塞投票操作，未听完也可直接投票。

**US-08 查看冠军路径**

作为注册用户，我想看到最终冠军是怎么一路赢上来的，以便回顾整场评选过程。

验收标准：

（1）结果页展示冠军专辑的封面、名称与所属歌手；

（2）以图形方式展示冠军从首轮到决赛的全部对战路径；

（3）展示每一轮的对手与得票情况；

（4）支持点击历史场次回顾该场对战的两张专辑。

**US-12 个性化解读**

作为注册用户，我想得到一段针对我个人作答的解读，而不是所有人一样的模板。

验收标准：

（1）解读文案的输入包含作答选项组合、各维度得分与最终类型；

（2）同一类型的用户，因作答组合不同可获得不同文本；

（3）接口调用失败或超时时，自动使用模板文案降级，界面不出现报错；

（4）解读生成后与测评结果一同入库，重复查看时直接读取，不重复调用接口。

## 四、功能需求

### 4.1 功能结构

系统分为前台用户端与后台管理端两部分。前台包含 9 个功能模块，后台包含 5 个功能模块。

### 4.2 前台功能模块

**模块一　首页与导航**

（1）展示平台定位与两种玩法入口；

（2）展示排行榜概览与近期热门专辑；

（3）全局导航与移动端适配。

**模块二　用户与账号**

（1）用户注册与登录，密码单向加密存储；

（2）登录状态维持与退出登录；

（3）个人中心：我的对决记录、我的测评记录、我的收藏；

（4）收藏与取消收藏。

**模块三　音乐数据浏览**

（1）按关键词搜索歌手；

（2）查看歌手的专辑列表与专辑详情（曲目、发行日期、曲目数）；

（3）数据缓存与过期更新策略。

**模块四　专辑对决**

（1）范围选择：按歌手、并支持流派与年代的筛选入口；

（2）对阵表生成：自动配对，处理参赛数为奇数时的轮空；

（3）逐场投票：每场展示两张专辑，用户二者择一；

（4）轮次推进：小组赛、复活赛、淘汰赛；

（5）冠军生成与结果汇总。

**模块五　试听播放**

（1）播放专辑的 30 秒试听片段；

（2）播放状态管理与互斥控制；

（3）无试听资源时的降级提示。

**模块六　音乐人格测评**

（1）测评说明页：玩法介绍与预计耗时；

（2）作答流程：12 道题，含至少 2 道听感题；

（3）计分模型：按选项累加各维度得分；

（4）类型映射：由得分分布映射到人格类型；

（5）结果展示：人格卡、维度得分、推荐专辑。

**模块七　AI 个性化解读**

（1）构造提示词，输入作答组合与得分；

（2）调用大语言模型生成个性化解读文本；

（3）超时与失败降级为模板文案；

（4）结果缓存，避免重复调用。

**模块八　结果可视化与分享**

（1）对阵图与冠军路径图绘制；

（2）人格卡绘制；

（3）导出为图片供保存与分享；

（4）分享记录入库，便于找回。

**模块九　排行榜与人格图鉴**

（1）全球最受欢迎专辑榜，按累计票数排序；

（2）榜单支持按范围筛选与分页；

（3）人格图鉴：展示全部人格类型及其占比分布。

### 4.3 后台功能模块

**模块十　数据看板**

展示用户数、对决次数、投票总数、测评完成数、人格类型分布等统计指标。

**模块十一　测评题目管理**

题目的新增、修改、删除与排序，以及每题选项与其对应分值的维护。

**模块十二　人格类型管理**

人格类型的类型码、名称、描述、推荐专辑的维护。

**模块十三　音乐数据管理**

查看缓存数据、手动刷新指定歌手数据、清理失效数据。

**模块十四　用户管理**

查看用户列表、检索用户、禁用违规账号。

## 六、非功能需求

### 6.1 性能需求

| 编号 | 需求项 | 指标 |
| --- | --- | --- |
| NFR-P1 | 首页首屏加载 | 常规网络下不超过 3 秒 |
| NFR-P2 | 普通业务接口响应 | 95% 请求不超过 800 毫秒 |
| NFR-P3 | 榜单查询响应 | 不超过 1 秒，列表分页返回 |
| NFR-P4 | 音乐数据获取 | 首次请求外部接口后落库，后续直接读缓存 |
| NFR-P5 | 并发支持 | 满足不少于 50 人同时在线访问的演示规模 |
| NFR-P6 | 大模型生成 | 设置超时上限，超时立即降级，不阻塞页面 |

### 6.2 安全需求

| 编号 | 需求项 | 措施 |
| --- | --- | --- |
| NFR-S1 | 密码安全 | 采用单向加密算法存储，数据库中不出现明文 |
| NFR-S2 | 身份认证 | 采用令牌机制，令牌设有有效期并校验签名 |
| NFR-S3 | 接口鉴权 | 需登录的接口统一校验令牌，后台接口额外校验角色 |
| NFR-S4 | 输入校验 | 所有入参做类型与范围校验，防止非法数据入库 |
| NFR-S5 | 防刷票 | 同一用户对同一场次只能投一票，重复提交被拒绝 |
| NFR-S6 | 密钥保护 | 大模型密钥与数据库连接串仅存于服务端，不下发前端 |
| NFR-S7 | 越权防护 | 用户只能访问与操作属于自己的记录 |

| NFR-U1 | 响应式布局 | 适配 360 像素及以上宽度的移动端与桌面端 |
| NFR-U2 | 外部依赖降级 | 外部音乐接口不可用时使用本地缓存数据 |
| NFR-U3 | 状态反馈 | 加载、空数据、错误三类状态均有明确提示 |
| NFR-U4 | 操作可逆 | 关键操作提供二次确认，避免误操作 |
| NFR-U5 | 时长可控 | 单次对决与单次测评的预计耗时在入口处告知用户 |

### 6.4 兼容性需求

支持主流浏览器的近期版本（含 Chrome、Edge、Safari），并适配 iOS 与 Android 移动端浏览器。

## 七、数据需求

系统围绕四类业务对象组织数据：用户、音乐数据、对决过程、测评数据，共设计 12 张数据表，分别为用户、收藏、分享图记录、歌手、专辑、曲目、对决、对战场次、投票、测评题目、人格类型、测评结果。

其中音乐类数据采用"外部获取 + 本地缓存"策略：首次访问时从开放接口获取并写入本地数据库，后续优先读取本地数据，既降低对外部接口的依赖，也避免触发接口调用频率限制。

数据表的具体字段与实体关系详见《系统设计文档》中的数据库设计章节与实体关系图。

## 八、约束与假设

### 8.1 约束条件

（1）音乐数据仅使用开放接口提供的元数据与 30 秒试听片段，不使用未授权的完整音频资源；

（2）平台不提供完整曲库播放能力，定位为评选与测评工具；

（3）大语言模型的调用存在费用与频率限制，必须有缓存与降级机制；

（4）演示环境使用云平台免费额度，并发能力有限。

### 8.2 假设条件

（1）假设用户使用的浏览器支持现代前端特性；

（2）假设所选取的歌手在公开音乐数据接口中存在可获取的专辑数据；

（3）假设用户在发起对决时有基本的音乐偏好判断能力。

## 九、需求优先级与实施计划

### 9.1 优先级说明

| 优先级 | 含义 | 处理原则 |

### 9.3 验收方式

（1）功能验收：逐条对照本文档用户故事的验收标准进行验证；

（2）性能验收：使用浏览器开发者工具测量接口响应时间与首屏加载时间；

（3）安全验收：验证密码非明文存储、未登录时受限接口被拒绝、重复投票被拒绝；

（4）兼容性验收：在桌面端与移动端浏览器分别完成一次完整流程。
