错位在哪、别人怎么做、我改了什么

你说"UI 布局很多还是错位的，适配也没做好"，要求"多方的对比、多参考大 V 尤其是音乐世界杯"。 这一页就是：先把 MUSIC CUP 按 375 真机视口量一遍（不靠猜）， 再用同一套几何判据量我们自己，最后给出改了什么、还剩什么。

2参照：MUSIC CUP 是怎么做的（375 真机视口实测）

说明：我把它按 375×780、isMobile、hasTouch 真实渲染后量的。 它的对战页我没能自动进入（搜索交互复现不了，试了 4 种方式）， 所以下表首屏与架构是实测，对战页的结论来自它的官方《How to Play》描述 —— 我明确标了哪条是实测、哪条是文档推断。
✅ 学到了

首屏就是一屏，营销内容推到首屏下面

实测：SECTION.screen home 高度正好 780；SECTION.home-seo 从 y=780 开始，高 3339
  • 它的应用界面和SEO 营销长文是两块，首屏只放应用
  • 我们首页把「游客提示条 + 注册入口 + hero + 两个大卡 + 共建条 + 榜单」全堆在一屏里，一屏放不下就得滚
  • 可借鉴：首屏只留"最能代表产品的 1~2 个动作"，其余下沉
⚠️ 没照搬

它没有底部 Tab 栏，只有右上角一排胶囊按钮

实测：A.rank-fab / BUTTON.mc-acc-fab / BUTTON.am-fab 全部 y=14 h=34，固定在右上角逐个排开
  • 它是单页流程式产品：搜歌手 → 选曲库 → 一路打完，不需要在 5 个模块间横跳
  • 我们有对决 / 人格 / 排行 / 我的四个独立模块，横跳是刚需
  • 你 10-15 已拍板"手机用底部、桌面用顶部" —— 这条不动，但可以把"次要入口"（收藏、共建）从 Tab 挪到页面内，减少 Tab 数量
✅ 学到了

模式切换用「文字 tab」，不用大卡片

实测：热门歌曲 / 随机歌曲 / 自选歌曲 三个文字按钮 h=24~26、12px，选中项加 ✓
  • 我们创建页把模式做成 4 张大卡（`.mode`），一屏只放得下 2 张，要滚
  • 它的做法一屏能看完所有模式，选中态一个 ✓ 就够
  • 可借鉴：把模式选择改成一行文字 tab，省下的空间给"已选摘要"
✅ 学到了

搜索框 17px、背景是 741×741 的大模糊光斑

实测：input y=452 h=26 font-size:17px；DIV.blob b1/b2 741×701、border-radius:50%
  • 17px ≥ 16px —— 正好避开 iOS 聚焦时自动放大页面这个坑（我们的规范也是 ≥16）
  • 它的深色底 + 两个巨型柔光斑，和我们的"音乐海洋调性 + 极光光晕"是同一条路 —— 这条我们对齐了
📌 我们更强

玩法完成度不输它

官方文档：最多 48 首、14 语种、小组 4 选 2 → 遗珠复活 → 1v1 → 冠军 → 晋级图 → 匿名公共榜
  • 我们：专辑级对决（不是单曲）、6 种模式、自选上限 100、跨歌手配对、对位赛、好友同玩、人格测评
  • 它明写"手機優先 / 14 種語言"；我们 375 实测横向溢出 0、小字 0、JS 错误 0
  • 结论：玩法层面已经领先，差的只在"手机上顺手"这一层 —— 也就是这一轮在做的事
⚠️ 它做得比我们差

它的点击热区只有 24~34px

实测：模式按钮 h=24~26、歌手 chip h=34、右上角胶囊 h=34 —— 全部低于 44px 的行业标准
  • Apple HIG ≥44×44pt、Material ≥48×48dp；WCAG 2.2 的 24px 只是底线
  • 它为了视觉极简牺牲了触控；我们不跟 —— 我们热区 <44px 已经做到 0 个
  • 这条是"参考但不照搬"的实证：大 V 也会为好看牺牲好用

必须先说清楚：这个探针我自己改了三遍才可信。 第一版报了 100+ 项，逐条查下来绝大部分是我自己的测量错误： ① 把全幅装饰背景层（.aurora、.vglow 光斑）算成"内容被裁/宽出" —— 它们本来就该比视口大； ② 拿跨网格行比底边，把"自动换行后不同行不等高"当 bug —— 其实行内完全等高； ③ 把 align-items:center 的行算成"不齐" —— 居中本来就是设计如此； ④ 把 object-fit:cover 的封面算成"变形" —— 那是裁切； ⑤ 在 scroll=0 处量"是否被 fixed 底栏盖住" —— fixed 不随滚动动，是测量伪影。 不把这些修掉，我就是在拿假数字说服你。修完才得到上面这张表。

4唯一的真 bug：底部操作条把 Tab 导航整个盖住

现象：在「创建对决」页和「我的对决」页，底部 5 个 Tab 导航完全消失。
项实测
根因.tabbar（全局底部 Tab）和 .mobar（创建页底部操作条）都写了 bottom: 0， 而 .mobar 的 z-index: 80 比 .tabbar 的 60 高 ⇒ 操作条把 Tab 栏整个盖住
量到的重叠.mobar 占 685~780（高 95），.tabbar 占 723~780（高 57）—— 重叠 57px，正好是整个 Tab 栏
连带问题页面主体只让位 96px，而底部其实是两条固定条（95 + 57 = 152px）⇒ 差 56px， 创建页最后一张模式卡（「按流派/年代」）中心 y=745 也落在操作条里
修法.mobar 改为 bottom: calc(var(--tabbar-h) + var(--safe-b)) —— 坐在 Tab 栏上方，两条都看得见； 页面让位改为 calc(var(--tabbar-h) + 104px + var(--safe-b))
验收同一探针复跑：/battle/create 与 /battle/mine 从"被底栏盖"变成 ✅ 0 项
为什么之前没发现：第四十一批的探针只查"横向溢出 / 小字 / JS 错误"三件粗事 —— 那些是"能不能用"，不是"对不对"。盖住导航不影响"能不能用"，但严重影响"好不好用"。 这就是这一轮要换判据的原因。

5间距节奏：从源头吸附到刻度

间距刻度本来就是现成的（--sp-1~8 = 4/8/12/16/24/32/48/64）， 但不少地方用了刻度外的值，块与块之间忽近忽远 —— 这就是你说的"错位感"的主要来源。
位置整改前整改后说明
首页区块（.home）[22, 18, 24, 24, 16][24, 24, 24, 24, 16].duo 的 22、.poolbar 的 18 → 归队 --sp-5
领奖台卡内部（.alb）[0, 15, 12, 11, 3][0, 12, 12, 12, 8]封面下 15、歌手行 11 → --sp-3；收尾行 3 → --sp-2
排行榜页头写死 margin-top:22pxvar(--sp-5)inline style 也归队
筛选行（.filter）22px 0 6px--sp-5 0 --sp-2排行榜 / 人格图鉴共用
领奖台徽章行margin-bottom:11pxvar(--sp-3)11 → 12，和卡内其他地方对齐
一次没成功的尝试（如实记录）：我本来想在 base.css 写一条 .home > * + * { margin-top: var(--sp-5) } 一劳永逸 —— 结果完全不生效。 原因：它和组件里的 .poolbar 特异性打平（都是 1 个类）， 而组件样式后注入，所以组件赢。我删掉了那条死代码， 改成回到源头逐个吸附，并在注释里写明了"不要在这里统一，会白写"。 教训：全局覆盖类规则在和组件样式打架前，先算特异性。

事项级别为什么还没做 / 打算怎么做

.types 两个 22pxP2人格图鉴页，源头还没定位到（不是 .filter）。等 T3 一起收
16 与 24 混用P2两个值都在刻度上，只是同一容器内不统一。属"选哪一档"的设计判断，不是错误
首屏信息过密T3参照 MUSIC CUP 的"首屏只放应用、营销内容下沉"，我们首页堆了 6 组内容。 要动的是信息架构（哪些上首屏、哪些下沉），这个要你拍板
