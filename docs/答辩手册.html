一GitHub 零基础

只需要懂三个词。别的都不用管。

1.1 先建立直觉：把 GitHub 当成"游戏存档"

仓库 REPOSITORY

你这个游戏的整个存档文件夹。音格的仓库叫 yinge。

提交 COMMIT

按一次"存档"。存完之后，随时能读回这一时刻的全部代码。

推送 PUSH

把本地存档上传到云端。只有上传了，老师才能点开链接看到。

关键区别（这是你之前困惑的点）：
提交 = 存在你电脑上（我做的事）　　推送 = 传到 GitHub 网站上（你点一下的事）
所以你会看到"提交很多次，但 GitHub 上没变化"——正常的，因为还没推送。

1.2 你只需要会点两个按钮

打开 GitHub Desktop（你电脑上那个黑色图标的软件）

1
看左边 "Changes" 有多少条改动 有改动说明我动过代码。你不用管具体是什么。
2
点左下角 "Commit to main"（蓝色按钮） 这一步叫"存档"。上方的 Description 随便写两个字也行，比如 update。这是可选的——我也能帮你做。
3
点上方的 Push origin 这一步最重要，也最常被忽略。点完等几秒，GitHub 网站上才会出现最新内容。
唯一要记住的一句话：看顶部按钮。如果写着 Push origin 就点它； 如果写着 Fetch origin，说明已经同步好了，不用点。

1.3 "退回"怎么办？——你说一句话，我来做

你担心的"改坏了想退回去"，其实有三道保险，都不需要你操作命令行：

保险什么时候用谁来做
备份目录我每次改你的重要文件前，都会先复制一份到 _backup\日期_事由\我自动做
Git 提交点每个阶段存一次档，可以精确回到"某个版本"我自动做
你开口你说"把 XX 退回上一版" / "退回到做 ER 图之前"我立刻做
实际操作演示（这就是我要做的）： 
# 1. 先看有哪些存档点
git log --oneline
# 输出示例：
# beed7f7 补齐论文工具链与专业图表生成   ← 最新
# d6500e8 工具链说明切换首选链路
# 4e6326b 开题报告改用 python-docx 直出引擎

# 2. 只想退某一个文件（最安全，推荐）
git checkout 4e6326b -- docs/开题报告.md

# 3. 整个项目退回到某个存档点
git reset --hard 4e6326b
你不需要记这些命令。你只要说人话，我翻译成命令。

1.4 唯一必须你亲手做的：推送

原因（上次说过，这里写清楚）：我这边的网络环境连不上 github.com（实测返回失败）。 代码能从 GitHub 下载，但推不上去。
所以 Push 必须你在 GitHub Desktop 点一下。这是整条链路上唯一需要你的环节，其余全归我。

1.5 怎么让别人（老师）看到这些文档？

这个问题分三层，结论先给：开一次 GitHub Pages，以后一个网址看全部。

情况能不能看说明
对方下载了 html 文件能看 双击用浏览器打开即可，不用装任何软件。前提是该 html 没有引用外部文件。
在 GitHub 网页上点 html只看到代码 GitHub 只当它是普通文件，不负责渲染成网页。这是平台规则，不是文件的问题。
开启 GitHub Pages能看，有网址 GitHub 免费提供的网页托管。开启后得到一个 https://joruine.github.io/yinge/ 这样的链接，任何人点开就能看。
为什么推荐 Pages：老师不需要登录 GitHub、不需要下载、不需要解压，点个链接就看完。 答辩时也是直接投屏演示，比翻本地文件体面得多。

开启步骤（只需做一次，约 1 分钟）

1
打开 https://github.com/JORUINE/yinge，点右上角 Settings 如果看不到 Settings，说明没登录，先登录。
2
在左侧菜单栏找到 Pages，点进去 位置在左侧列表偏下方，在 "Actions" 和 "Security" 附近。找不到就按 Ctrl+F 在页面上搜 "Pages"。
3
Source 选 Deploy from a branch Branch 选 main，右边文件夹选 /docs，然后点 Save。
4
等 1 分钟，刷新这个页面 顶部会出现一条绿色提示，里面就是你的网址：https://joruine.github.io/yinge/
5
把网址发给我，我验证一下能不能打开 以后每次我改完文档，你 Push 一下，网址上的内容就自动更新了，链接不用换。
一个前提：仓库必须是 Public（公开）。免费账号的 Pages 只支持公开仓库。
这意味着文档里的姓名和学号对任何人可见——毕业设计本来就要署名，一般没问题； 如果你不想公开，告诉我，我改用"打包成 PDF 发微信"的方式，只是没法做在线链接。

三答辩讲解卡

六个必被问到的问题。每张卡：我们做了什么 → 为什么这么做 → 你照这个说。

技术选型

Q1：为什么不用网易云音乐的接口？

我们做了什么：最早确实走的是网易云第三方接口，实测发现它对本机网络启用了风控， 登录和取播放地址都返回 code: -462，连本地也调不通。后来换成 iTunes Search API。

为什么这么做：iTunes 接口不需要密钥、不需要登录、不会被风控，任何域名都能调， 而且官方提供 30 秒试听片段——这让我们能在不触碰版权问题的前提下，拿到真实可播放的音乐数据， 并且项目可以公开部署上线。

这样讲："我在数据源上做过两次迭代。最初用第三方非官方接口， 实测存在风控和版权风险，无法部署到公网。后来改用 iTunes 的开放接口， 它免密钥、提供官方试听片段，规避了版权风险，也让作品具备可公开访问的能力。 这个取舍是从'能不能真的上线'倒推出来的。"
系统架构

Q2：为什么要做前后端分离？

我们做了什么：前端 Vue 3 只负责界面和交互，后端 Node.js + Express 负责业务规则， 中间用 REST 接口通信，数据存 MongoDB。

为什么这么做：（1）规范赛道 C 明确要求"后端完整"； （2）音乐数据和大模型密钥绝不能放在前端，必须由后端代理； （3）前端可以独立部署到静态托管、后端独立部署到云应用平台，两边互不干扰。

这样讲："我把界面和规则分开。前端只负责呈现和收集操作， 所有业务判断——比如投票怎么计、冠军怎么产生——都在后端。 这样做的直接好处是密钥和数据不出现在浏览器里，而且前后端可以分别部署和扩容。"
核心算法

Q3：对决赛制是怎么设计的？

我们做了什么：用户选定范围后，系统抓取该歌手的全部专辑，自动生成对阵表； 先小组赛两两 PK，再插入复活赛，最后淘汰赛出冠军。

关键难点：专辑数量往往不是 2 的整数次幂（比如 11 张）， 直接两两配对会出现"落单"的专辑。所以要处理轮空（bye）问题。

为什么加复活赛：纯淘汰赛"输一场就没了"，用户投到一半容易失去动力。 复活赛既保住悬念，又不显著拉长时长。

这样讲："赛制设计里有两个实际问题。 第一，专辑数通常不是 2 的幂，必须处理轮空，否则对阵表会有一张专辑没有对手； 第二，用户完成率。纯淘汰赛在小组赛后流失明显，所以我加了复活赛。 这两个决定都是用'完成率'这个指标倒推的，不是拍脑袋。"
核心算法

Q4：音乐人格测评怎么保证结果不是随机的？

我们做了什么：12 道题，每题选项对应若干维度的分数； 作答完成后累加各维度得分，映射到人格类型。

为什么这么做：（1）每道题的分数是预先设计的，不是答题后随机生成； （2）包含听感题（要听了 30 秒片段再答），这是音乐类测评区别于普通问卷的地方； （3）同一份答案必然得到同一结果，保证可复现。

这样讲："测评不是随机贴标签。每道题的每个选项都对应维度权重， 后台有一张计分表，答完累加再映射成类型。相同答案一定得到相同结果，所以是可验证、可复现的。 另外我加了听感题——必须听了音乐才能回答，这是音乐测评和普通问卷的本质区别。"
加分项

Q5：AI 用在哪里？（规范里这是加分项）

我们做了什么：人格测评出结果后，把作答组合 + 类型 + 得分分布作为输入， 调用大语言模型生成一段个性化解读文案。

为什么这么做：传统 MBTI 类测试"同一类型的人拿到一模一样的文案"， 个性化程度低。用大模型可以让解读贴合这个人的具体作答。 同时要设计降级机制——接口失败时用模板兜底，界面上不暴露错误。

这样讲："AI 在我的项目里承担的是生成个性化文本， 不是核心逻辑。计分、类型映射这些是可复现的规则，不依赖 AI。 大模型只负责把结果写成人话，并且我做了失败降级——接口不通时用模板文案兜底， 保证功能不会因为第三方故障而不可用。规范把 AI 接入列为加分项，这也是我的加分点。"
数据库设计

Q6：12 张数据表是怎么设计出来的？

我们做了什么：先把业务对象分四类——用户域、音乐数据域、对决域、测评域， 再从每类里提取实体，最后确定关系和主外键。

设计取舍：专辑、曲目这些外部数据也落库缓存，而不是每次现查。 原因是降低外部依赖、提高响应速度、规避接口调用频率限制。

这样讲："我按业务域分组设计的，四个域对应四块功能，不是先建表再想用途。 另外我特意把外部音乐数据持久化到本地——因为如果每次打开页面都去调外部接口， 一旦接口限流整个系统就瘫了。缓存这一层让系统具备离线可用性。"

四架构与流程

4.1 系统架构（三层 + 外部服务）

怎么读这张图（从上往下）：

  • 客户端：用户打开浏览器就用，不用装东西。
  • 展示层：6 个模块的页面。它不含业务规则——比如"哪张专辑赢了"不是前端能算的。
  • 业务服务层：系统的"大脑"。认证、抓歌并缓存、赛制生成、投票计分、榜单统计、后台管理，全在这里。
  • 数据层：MongoDB，12 张集合，只存不判断。
  • 外部服务：iTunes 拿音乐（含 30 秒试听）、大模型写解读。都是后端去调，前端碰不到密钥。

4.2 数据库设计（ER 图）

答辩时的讲法：别一张张念表。按四个域讲——

用户域

用户、收藏、分享图记录
对应"登录和我的内容"

音乐数据域

歌手、专辑、曲目
外部数据抓来后落库缓存

对决域

对决、对战场次、投票
一次对决 = 1 条对决 + N 条场次 + M 条投票

测评域

测评题目、人格类型、测评结果
题目 → 作答 → 结果 → 归属类型

4.3 一次对决，数据是怎么跑的

这段一定要能顺口讲出来，它是"数据驱动"（规范第 3 条硬要求）最直接的证据：

1
你在页面选了"周杰伦" 前端把关键词发给后端 → 后端先查本地缓存，没有才去 iTunes 要 → 拿到专辑列表后存进 albums 表 → 返回给页面
2
点"开始对决" 后端生成对阵表，写 1 条 battles 记录 + N 条 battle_matches 记录（每一场是左右两张专辑）
3
你点某个封面上的"试听" 播放的是曲目表里存的 previewUrl（30 秒官方片段）——数据在第一步就存好了，不用再请求外部
4
你投票给左边这张 写 1 条 votes 记录 → 同时更新该场次的 winnerAlbumId（谁赢了）→ 下一轮对阵据此生成
5
最后一场投完 写回 battles.championAlbumId（冠军）→ 榜单统计时聚合所有 votes，得出"全球最受欢迎专辑"
6
点"生成分享图" 写 1 条 share_cards 记录，保存这张图的归属，方便你在"我的分享"里找回
被问"你怎么证明不是静态页面"时的答案： "从选歌手到出冠军，全程产生 5 类新数据：专辑缓存、对决记录、场次记录、投票记录、分享记录。 把这些表清空，系统就跑不起来；投完票后榜单的数字会变化。页面不是写死的，是数据算出来的。"

4.4 人格测评的流程

1
读题 从 personality_questions 按 order 顺序取 12 题；含听感题的会带一个 30 秒试听
2
作答 每题选项带预置分值，前端只收集选项，不在前端算分
3
后端算分 累加各维度得分 → 按映射规则得到 typeCode → 写 1 条 personality_results
4
生成解读 把作答组合丢给大模型写个性化文案；失败则用模板兜底
5
出卡 人格卡（可导出图片）+ 推荐 3 张专辑 + 归入人格图鉴
两个玩法为什么算"一套底层"：都要登录（用户系统）、都要音乐数据（缓存表）、 都要生成图片（分享图）、都要统计（榜单）。所以做完一个，另一个是复用，不是重做。 这也是工作量能撑起毕业设计的原因。

5.2 我建议的下一步：需求分析文档

为什么先做它：规范把它列在第一个。它还是后面所有东西的源头—— 界面稿要做哪些页面、数据库要有哪些字段、接口要开哪些，都从这里推导。跳过它， 后面就会出现"做着做着发现少个页面"。

我会产出什么：

格式：Word（走已验证的通路，带目录与页码），同时给一份可视化 HTML 方便你看。
