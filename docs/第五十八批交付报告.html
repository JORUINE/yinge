实话先说在前：我用真实链路（真提交测评 → 真结果页 → 真导出按钮）把 六种人格卡逐个导出了， 也把竖版/方形分享卡导了 —— 在我这台机器上六张全是对的（图片见附件）。 也就是说"只有旋律捕手正常"这个现象我复现不出来；这通常意味着它跟**真机（iOS/WebKit）或图片加载时序**有关，不是版式算错。 所以我没有停在"看起来没问题"，而是做了三类**机制级**加固 + 全量自检。
#加固点为什么
1.sbg 不再用 CSS transform: scale(1.16)，过扫改画进 canvas（1.18 倍） 导出是「克隆 → 内联样式 → SVG」，transform 是克隆树里最容易出偏差的东西。 你那张竖版分享图"封面没了、原地一块灰色圆角方块"，正是背景层被缩放后的残影形态。现在背景层没有 transform 可错了。
2出图后再解一遍（pngSeemsRight） 验的是"用户真正会存下来的那份文件"：能解码 + 颜色数够 + 每张封面位置不是整片纯色。不达标就换引擎重来。 你在 iOS 上那张 2.1 MB 却打不开的 PNG，就是这一步要拦的。
3逐图数颜色（imagesSeemPresent，上一批已加）继续生效 "图丢字留"时体积很大，只看大小永远放行。
全量自检（_r58-verify.mjs，26 条全绿）： 六种人格卡逐个导出，每张都断言 尺寸 1080×1440 + 中心区亮度与页面背景图一致 + 透明像素 <0.02%。 分享卡横竖断言 导出比例 = 预览比例（0.6186 vs 0.619 / 1.0000 vs 1.000）+ 满幅背景铺满。
六型实测（页面背景亮度 vs 导出中心亮度） CLM 84.8 / 108.4 EXP 63.9 / 82.4 LYR 189.2 / 211.9 MEL 19.8 / 30.4 RHY 134.4 / 193.4 TMB 218.6 / 224.4 —— 全部不透明、颜色数 194~416；"背景没画上"会是 255 对 20~220，差 100+，一定被抓出来
还需要你做一件事：把 iOS 上导出失败的那张原图（保存出来的文件）发我一张。 我这边六型都对，说明问题在真机链路；有那张文件我能从它的像素反推是"哪一层丢了"，比继续猜快得多。
