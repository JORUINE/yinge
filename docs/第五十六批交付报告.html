1真机还是丢图 —— 这次找到了"为什么只有这几处丢"

上一批修好了分享卡（分享页、方形/竖形图），但你说 对位赛战报 / 结算分享 / 人格卡 还是丢。 把这三处的 <img> 全部捞出来逐个看，差别只有一处：

位置上一批状态后果
BattleShareView（分享页）有 crossorigin="anonymous"导出正常
PersonalityCard（人格卡）有正常
对位赛战报 / 结算页 / 晋级图 / 对位小卡没有丢图
根因（一句话）：没写 crossorigin 的 <img> 浏览器按 no-cors 模式拉图 —— 图在页面上照常显示，你看不出任何问题；但把它画进 canvas 时画布会被污染， toDataURL() 直接抛 SecurityError。上一批的"canvas 重绘优先"在这几处救不回来， 因为污染是图片加载方式决定的，不是代码写法决定的。

修了两件事：

  • 给 BattleResultView（10 处）、BracketTree、AlignedMiniCard 的封面 img 全部补上 crossorigin="anonymous" —— 共 13 个 img 标签。
  • 补第三条兜底：万一还有漏网的（比如某个旧组件、某张图是后来动态插进来的），导出前用 crossOrigin='anonymous' 重新加载一次再画进画布。 同时加了零尺寸保护（naturalWidth=0 时 0×0 画布会静默产出空白图）。
  • 反过来的风险也堵了：加了 crossorigin 后，如果某张图的服务器不回 CORS 头， 浏览器会直接拒绝渲染（ = 页面裂图，比"导出丢图"更严重）。所以新增 utils/imgSafe.js：全局捕获 img 的 error， 去掉 crossorigin 重试一次 ⇒ 最坏退回"能看但导出丢这一张"，永远不会从"能看"变成"裂图"。
验证方式（可复现）：探针里故意拦断所有跨域 fetch（真机级复现）， 再点「保存晋级图」拿真实下载到的 PNG 数像素：410.6 KB / 1080×2279 / 622 种颜色（空白图会是个位数颜色）。 上一批同样的方法测分享卡是 387 色。

根本无法看全见下内容宽 640 → 362px，横向溢出 0

"看不全"到底卡在哪：晋级树的内容宽 = 第一轮并排几张卡 × 卡宽（16 张专辑就 1500px+）， 塞进结算页那张卡里只能横着拖。全屏子页先解决"地方不够"，再用 zoom 自适应把宽度压到一屏。 但只压宽度会踩守则：竖版清单写死 640px，压到 390 屏就是 zoom 0.609， 12px 的专辑名会被压成 7.3px（违反"任何文字 ≥12px"）。所以竖版清单在子页里改成流式宽度， zoom 直接回到 1.0，字保持原大小。横版树本来就宽（scrollWidth 约 1500px）， 这时「适应宽度」自动算到 0.492 —— 这正是它该干的活。

自己踩过的坑（记下来）：判断"还有没有横向溢出"时， 一开始用 元素.scrollWidth - 容器.clientWidth，报了 250px 溢出 —— 其实缩完只占 390px。因为 scrollWidth 是元素自己的 CSS 像素，不受祖先 zoom 影响。 判据改成"getBoundingClientRect().width ≤ 容器宽"+"容器自己还滚不滚得动"之后才为真。

3对位赛战报「上面字体有问题」

为了拿到真证据，给 dev 造局接口加了"对位赛"档位（POST /api/dev/battle 传 scopeType:'aligned'），这样探针能一键造出"前一半 vs 后一半"的逐行对照局，直接导出战报图。

要跟你说实话：我这台机器上没能复现。导出图 1080×5318， 量了顶部 14% 区域的"文字行分布"：99-140 / 260-361 / 442-490 / 565-604 / 712-744， 和页面几何一致，没有叠字、没有换行、没有裁切（截图我也看了）。

但这类 bug 的成因上一批已经确认过一次，而且它是字体度量相关的 —— 所以在我这套字体（Linux 的 fallback 字）下不复现、在你手机上复现，完全说得通：

导出走的是「克隆 → 内联 computed style → SVG foreignObject」，克隆体在另一个文档里渲染， 字体度量和你手机上的真字体可能差零点几像素。而 .arep-top / .arep-score 是弹性布局， 子项默认是"自动尺寸"⇒ 差一点就会在文字内部换行/压缩 ⇒ 保存下来就是"字挤在一起 / 排版错乱"。 第五十五批在分享卡的方形图上正是栽在这（专辑名叠在一起，页面上却正常）。

所以按同一口径做了结构性加固：顶部四块（品牌行、大比分、领先说明、积分胶囊）的 所有子项一律 flex:0 0 auto + white-space:nowrap —— 不许内部换行、不许被压缩；真放不下时由容器 flex-wrap 在元素之间换行， 而不是把一行字劈开。宽度够的时候观感完全不变。

需要你配合一次：如果改完保存下来还是有问题，把那张保存下来的图发我（不用截图页面，要保存出来的那张）。 因为没有那张图我只能按"这一类 bug 的通用成因"加固，没法对症。

5手机端"点了播放会延迟一会儿" —— 改的都是可量的

延迟从哪来：原来点播放要等两段网络 —— ① 拉曲目表 GET /music/albums/:id/tracks （后端还要顺带同步 iTunes 片段）② 下载 30 秒音频。第一段完全没必要等。

改动改前改后
曲目表缓存（同一局里曲目不会变）来回切三张专辑 = 3 次 /tracks2 次（第一张预热 + 第二张首次），再切回不再请求
空闲预热（requestIdleCallback，最多等 2 秒）进页面 0 次请求进页面就 2 次（1v1 的两张；小组赛只预热前 2 张，控制流量）
<audio preload="auto">点播放才开始拉音频地址一设好就开始缓冲
进度更新节流（只按"秒"更新）这项如实说：我在无头浏览器里量到改前改后都是 3 秒 3 次（这台机器上 timeupdate 本来就≈1Hz）， 没法证明它在你手机上有收益。但规范允许它每秒触发 66 次，所以这条作为预防性加固留着，不是本轮的主功。
没有阉割任何动效：转盘旋转、声纹、阶段过场、按钮按压反馈、玻璃质感一个都没删， 改的全是"少做无意义的重复计算"。
改前（dist-before-56b @5174）： 进页面 /tracks = 0　｜　切歌 1 → 2 → 3（每次都新请求） 改后（dist @5173）： 进页面 /tracks = 2　｜　切歌 2 → 2 → 2（缓存命中） 播放中 3 秒 DOM 变更 = 4 次（音频确实在播：paused=false, currentTime 2.39→5.70）
