音格 · 前端设计工作守则

本守则汇总祖锐在历次沟通里提出的前端设计意见。当前阶段：功能优先 —— 先把功能与数据全部落实，前端视觉与动效统一放到收尾阶段，届时按本守则逐条对照落实，不再事后返工。

0总原则（先定调，再动手）

① 功能优先，前端与动画后置。功能未落实完之前，不做纯视觉打磨与动效；但功能性 bug（数据错、算错、点不动）立刻修。
② 唯一视觉基准是设计稿。docs/design/音格-UI设计稿.html。做页面时逐屏对照；实现出来和 demo 不一样 = 没还原到位，不是"可以接受"。
③ 可读性是不可谈判项。排版一乱、字一小说"后面再优化"，到收尾就是灾难 —— 所以收尾阶段要专门过一遍本守则第 1、2 节。
④ 借鉴可、照搬论据不可。竞品的交互/动效可以学，但规则必须用音格自身产品逻辑说通（原话："我们不是音乐世界杯，是专辑比拼，是音格"）。

1可读性（字与密度）

来源：投票页截图反馈 —— "说明的字体也很小"。

项要求当前问题
正文/说明字号≥ 14px；页面说明、提示、次级文字 ≥ 13px；不得用 10–11px 承载需要阅读的信息待修 投票页/创建页的说明与专辑元信息偏小（实测观感约 11–12px）
专辑卡内文字专辑名 ≥ 15px、歌手名 ≥ 13px；不要把封面当唯一主角而把文字压到看不清待修 投票卡专辑名/年份偏小
对比度正文对比 ≥ 4.5:1；浅色底上不用 #7c97a8 这类淡色承载正文复核
信息层级一屏内主信息 1 个、次信息 2–3 个，其余收进详情复核

2布局（必须对齐 demo）

来源：参赛池截图反馈 —— "这里明显前端界面都出问题了…我们设计demo里是这样的吗"。

不是 demo 的样子。demo 里参赛池是 7 等分正方形网格（封面等高、圆角一致、间距一致、名称单行省略），现在渲染出来封面大小不一、排布散乱 —— 属实现没还原到位，收尾阶段必须修成 demo 那样。
  • 网格类布局一律用 grid + repeat(n, minmax(0, 1fr))；封面统一 aspect-ratio:1 + object-fit:cover。
  • ⚠️ 绝对不要写裸 1fr：1fr 等价于 minmax(auto,1fr)，一旦单元格里是 white-space:nowrap 的长文本（如真数据里的长专辑名），该列会被内容**撑宽**，整片网格就变成大小不一。这就是 2026-09-17 参赛池"封面大小不一"的根因。所有网格列一律写 minmax(0, 1fr)。
  • 排布要密实，不要大片留白；宽屏下按容器宽度自适应列数（如 7 / 5 / 3 挡）。
  • 长名称统一单行省略（text-overflow:ellipsis），不允许换行把网格撑歪。
  • 同类卡片在同一页内尺寸必须一致（不做大小混排，除非 demo 明确要求）。

3玩法呈现：盲盒原则（重要）

来源：参赛池截图反馈 —— "灰掉的专辑是这轮对决没随机到的吗…参赛池预览没必要展示选出的每位歌手这轮出战的所有专辑，有个一两张就行，不然这个随机比拼的刺激性就没了，应该像盲盒一样。后续甚至可以加入动画，像抽卡一样进入对决。"

① 不要剧透。创建页的「参赛池预览」不展示每位歌手本轮全部出战专辑，每位 露出 1–2 张即可，其余留白/示意。保留"不知道会抽到谁"的刺激感。
② 进度条也要配合。创建页只给"共 N 张 / 共 M 步"这类总数，不逐张列出全部名单。
③ 出场要有仪式感（后续）。进入对决时做 抽卡式动画（洗牌 → 翻出本轮对阵），把"随机"这件事变成体验的一部分。
实现备注：后端已按规模分好组，前端只需控制展示粒度（曝光上限 + 动画），无需改赛制。

4交互与反馈：让人知道"我在哪"

来源：对比 musiccup 后的总结 —— 痛点不是"场次多"，而是"没有阶段感 / 没有回馈 / 不知道我在哪"。

  • 阶段动效：进入小组赛 / 复活赛 / 淘汰赛各给一次明确的阶段切换提示。
  • 进度常驻：已投 X / Y 步 一直可见（现在已有）。
  • 返回重选：选错了要能退回上一步（现在小组投票只支持"清空重选"，需补"返回上一组"）。
  • 落败置灰：淘汰赛落败的专辑置灰，让"战况"留在页面上。
  • 迷你对阵树：投票页给一个随时可见的小对阵图。
  • 动画克制：入场淡入、hover 位移 150–300ms；尊重 prefers-reduced-motion。

C · 你提的原创想法

  • 盲盒原则：参赛池不剧透全部出战专辑。
  • 抽卡式入场动画：洗牌 → 翻出本轮对阵，把"随机"做成体验。
  • 对决要有阶段感 / 回馈 / 「我在哪」（痛点不是场次多，而是不知道进行到哪一步）。

D · 明确不做（免得以后重复讨论）

  • 不做「选代表曲」环节：对决对象是专辑不是单曲，"代表曲"只帮你听个大概、不参与计票。
  • 不做音频可视化 / 3D 类视觉（超出本作品范围）。
  • 借竞品只借交互与动效，规则论据必须用音格自身产品逻辑（我们不是音乐世界杯，是专辑比拼）。

7需要专门研究的问题

这两条不是"排个版就完事"，是要先想清楚再动手。

① 测评题量与听感题占比

用户的疑问："十二道题目会不会太局限 我感觉听感题目两道太少了 这里必须研究下怎么优化。"
  • 题量：12 题约 3 分钟；要评估"加到 16~20 题"对完成率 vs 区分度的影响（题太多会劝退，太少则 6 个类型分不开）。方向：先按 16 题设计（4 维度各 4 题），保持 3~4 分钟。
  • 听感题：从 2 道扩到 4 道左右。听感题是"音乐测评 ≠ 普通问卷"的核心差异，只有 2 道确实撑不住。
  • 音频来源（关键）：现在听感题没有真实音频。可行做法 —— 从 iTunes 30 秒片段里固定挑几段绑到题目上（后台可维护 audioRef），保证所有人听的是同一段（可复现、公平）。绝不能用随机片段。
  • 验收标准：每道听感题都能真实播放、且不同人打开听到的是同一段。

② 歌曲 API / 播放能力到哪一步

用户的疑问："还有什么时候接入歌曲api。"
  • 现状（已经接好了）：数据源就是 iTunes Search API，专辑曲目自带 30 秒试听地址（previewUrl），免密钥、免登录、可公开部署。
  • 要定的只有一件事：是否需要"完整播放"。完整播放涉及版权与密钥（网易云路线已证实会 -462 风控），建议不做，维持 30 秒试听。
  • 真正要补的是体验：把 30 秒试听做"完整"—— 显示歌名、支持上一首/下一首、显示序号（1/10）（见第 16 条）。这才是用户能感知的差别。

8落地方式

  • 守则长期有效：每次做前端都先读它；提新意见时追加进本文件，不散落在聊天里。
  • 收尾阶段按第 5 节清单逐条打勾，并把修改前后截图附在《自检清单》里，不靠"我觉得改好了"。
  • 与《自检清单》分工：自检清单管对错（数字/状态/口径），本守则管好看好读好用。
